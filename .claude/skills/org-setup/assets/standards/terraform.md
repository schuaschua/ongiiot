# Terraform standards (org baseline)

> **Org baseline, version 1.0.0** (Org Kit, module `org`). Projects copy this file into their standards folder and extend it: fill in the placeholders, name their stacks, add project rules below the baseline ones, and record any deviation under [Accepted exceptions](#accepted-exceptions). Never delete or weaken a baseline rule silently.

Applies to everything under `infra/`. The project's architecture document is binding: where this file and the architecture disagree, raise it and fix one of them. Azure resource naming, tagging and region rules are in [azure.md](azure.md) and are not repeated here.

Placeholders: `<project>`, `<env>`, `<rgn>` and `<org>` as in azure.md; `<stack>` is one of the environment's stacks.

Sources: TFBP = [terraform-best-practices.com](https://www.terraform-best-practices.com/); AVM = [Azure Verified Modules](https://azure.github.io/Azure-Verified-Modules/).

## Directory tree

```text
infra/
  bootstrap/
    state-backend.sh      # az CLI, idempotent: state storage, project RG, deployment identity. Run once, outside Terraform.
    README.md             # how to run it; any manual one-off steps (e.g. database principal bootstrap)
  modules/                # project modules that compose AVM modules; no provider or backend blocks
    <name>/
      main.tf
      variables.tf
      outputs.tf
      versions.tf         # required_providers only (no provider config)
      README.md           # generated by terraform-docs
  <env>/                  # one folder per environment; environments share nothing
    <stack>/              # e.g. foundation (long-lived platform) and app (fast-changing workload)
      main.tf
      variables.tf
      outputs.tf          # values later stacks need
      versions.tf         # required_version, required_providers, backend "azurerm"
      providers.tf        # provider "azurerm" / "azapi" configuration
      locals.tf           # optional: derived names, common tags
      terraform.tfvars    # environment values; no secrets
      .terraform.lock.hcl # committed
      data.tf             # only in later stacks: terraform_remote_state reads
```

## Apply order (per environment)

The project's architecture defines its stacks and their order; a typical order is:

1. Once per subscription: run `infra/bootstrap/state-backend.sh`. It creates the state storage, the project resource group, the pipeline's deployment identity with its role assignments, and the resource provider registrations (azure.md rule 31).
2. First stack (e.g. `infra/<env>/foundation`): `terraform plan -out=tfplan`, human approves, `terraform apply tfplan`.
3. Any one-off manual step recorded in `infra/bootstrap/README.md` (e.g. creating database principals for the runtime and pipeline identities).
4. Build and push images (e.g. `az acr build`, outside Terraform).
5. If your project uses database migrations: run them from the CI runner (outside Terraform; rule 36).
6. Later stacks: plan, human approves, apply the saved plan.
7. Post-deploy smoke check.

Destroy in reverse order, only through the pipeline's destroy workflow (started by hand on `main`, with a typed confirmation), never locally.

## Rules

### Layout & stacks

1. Keep the medium layout: shared modules in `infra/modules/`, one root folder per environment and stack under `infra/<env>/<stack>/`. ([TFBP: medium-terraform example](https://github.com/antonbabenko/terraform-best-practices/tree/master/examples/medium-terraform))
2. Each environment has the stacks the architecture defines, and the architecture assigns every resource to exactly one stack. Moving a resource between stacks is an architecture change. If a later stack must change a resource an earlier stack owns (e.g. a container image), the owner declares `lifecycle.ignore_changes` on those attributes and the later stack sets them with `azapi_resource_action` (`PATCH`); two stacks never both own one resource.
3. Environments share nothing: no cross-environment remote-state reads, no shared state, no shared tfvars. ([TFBP: medium-terraform example](https://github.com/antonbabenko/terraform-best-practices/tree/master/examples/medium-terraform))
4. Every root contains the standard file set shown above; modules contain `main.tf`, `variables.tf`, `outputs.tf`, `versions.tf` and no `terraform.tfvars`. ([TFBP: Code structure](https://www.terraform-best-practices.com/code-structure))

### State

5. Store all state in the `azurerm` backend created by the bootstrap script, one key per stack: `<env>/<stack>.tfstate`. Never commit state or keep it local. ([TFBP: Code structure](https://www.terraform-best-practices.com/code-structure))
6. Configure the backend with `use_azuread_auth = true`; no storage account keys or SAS tokens.
7. Stacks exchange values only through `data "terraform_remote_state"` reading an earlier stack's outputs. Earlier stacks never read later ones. ([TFBP: Key concepts](https://www.terraform-best-practices.com/key-concepts))
8. Expose only what the consumer stack needs as outputs; a later stack must not look earlier stacks' resources up by name with data sources.

### Providers & versions

9. Use the latest stable (non-preview) versions of Terraform, the providers and each AVM module at the time the code is written, and pin them exactly in every root so builds are reproducible. Upgrades are deliberate: bump the pin, run `plan`, and update the version table in the architecture.
10. Commit `.terraform.lock.hcl` for every root.
11. Configure providers only in a root's `providers.tf`; modules declare `required_providers` and never contain `provider` blocks. ([TFBP: Key concepts](https://www.terraform-best-practices.com/key-concepts))
12. Use `azurerm` for hand-written resources; use `azapi` only where `azurerm` does not model the resource (e.g. Container Apps `authConfigs`, Foundry data-plane resources), plus the cross-stack patch in rule 2. Add a comment naming the missing `azurerm` resource.

### Modules (AVM first)

13. Use an Azure Verified Module whenever one fits: `source = "Azure/avm-res-<service>-<resource>/azurerm"` (or `avm-ptn-*` for patterns). Check the [AVM Terraform resource module index](https://azure.github.io/Azure-Verified-Modules/indexes/terraform/tf-resource-modules/) first. ([AVM: module specs](https://azure.github.io/Azure-Verified-Modules/specs/tf/))
14. Pin every AVM module to an exact `version = "x.y.z"`, never a range.
15. Only use AVM modules marked Available; for Proposed or missing modules (e.g. consumption budget) hand-write the resource per rule 12.
16. Set `enable_telemetry = true` explicitly in every AVM module call (telemetry kept on). ([AVM: solution development](https://azure.github.io/Azure-Verified-Modules/usage/solution-development/terraform/))
17. Compose AVM modules in `infra/modules/<name>/`; roots call `infra/modules/*` or AVM modules, never other roots.

### Naming & style

18. Use lower `snake_case` for all Terraform identifiers (resources, data sources, variables, outputs, locals); dashes only in Azure resource name values (see [azure.md](azure.md)). ([TFBP: Naming](https://www.terraform-best-practices.com/naming); [AVM: TFNFR4](https://azure.github.io/Azure-Verified-Modules/specs/tf/res/))
19. Do not repeat the resource type in the name (`azurerm_container_app.api`, not `.api_container_app`); use `this` only when a module has one resource of that type. ([TFBP: Naming](https://www.terraform-best-practices.com/naming))
20. Argument order: `count`/`for_each` first, then arguments, `tags` last, then `depends_on`, then `lifecycle`. ([TFBP: Naming](https://www.terraform-best-practices.com/naming))
21. Code must pass `terraform fmt -check -recursive` and `terraform validate`. Comments use `#` only. ([TFBP: Code styling](https://www.terraform-best-practices.com/code-styling))

### Variables & outputs

22. Every variable and output has a `description`; variable keys ordered `description`, `type`, `default`, `validation`; plural names for lists and maps; no double negatives. ([TFBP: Naming](https://www.terraform-best-practices.com/naming))
23. No hardcoded environment values in `main.tf`; they come from `terraform.tfvars` or `locals.tf`. ([TFBP: Code structure](https://www.terraform-best-practices.com/code-structure))

### Secrets & identity

24. No secrets in `.tf`, `.tfvars`, outputs or commits. Generate application secrets (e.g. token signing keys) with `random_password` and write them directly to the platform secret store; mark related outputs `sensitive = true`.
25. Services authenticate with managed identity and role assignments declared in Terraform; no passwords or keys for databases, registries or AI services.

### Workflow (plan/apply/approval)

26. Always `terraform plan -out=tfplan`, have a human review and approve that plan (in CI, the owner reviews the plan on the pull request into `main`, then starts the deploy run, rule 33), then `terraform apply tfplan`. Never `apply -auto-approve` and never apply without a saved, approved plan.
27. Apply stacks strictly in the architecture's order; a failed step stops the sequence.

### Forbidden

28. No `local-exec`, `remote-exec` or `file` provisioners, and no `null_resource`/`terraform_data` used to run scripts.
29. No portal or CLI changes to Terraform-managed resources. The only out-of-band steps are the state-backend bootstrap, image builds, the pipeline's migration step with its temporary firewall rule (rule 36), and one-off steps recorded in `infra/bootstrap/README.md`.
30. No `terraform import`, `state mv/rm` or `-target` without a note in the PR explaining why.

### CI/CD (GitHub Actions)

31. All code lives in one GitHub repository per project; workflows are YAML in `.github/workflows/`.
32. On every pull request, a workflow runs `terraform fmt -check`, `validate` and `plan` for each stack and posts the plan as a PR comment.
33. Merges to `main` never apply. The owner starts the deploy workflow by hand (`workflow_dispatch`) on `main`, in the GitHub Environment `<env>` (deployment branch policy: `main` only); that manual run is the human approval in rule 26. `workflow_dispatch` is its only trigger; it deploys only the current `main` HEAD, one run at a time (queued, never cancelled), and fails on any destroy or replace of stateful or long-lived resources (databases, the Container Apps environment, AI accounts). It runs in the apply order above. Destroying uses a separate destroy workflow the same way (manual, `main` HEAD only, same queue, never cancelled): a run with mode `plan` shows the destroy plans for review, and a second run with mode `destroy` and the typed confirmation of the resource group name applies them; the destroy/replace guard does not apply there.
34. Workflows log in to Azure with OIDC workload identity federation. No stored Azure secrets; the tenant, subscription and client IDs are non-secret repository variables.
35. State stays in the Azure Storage backend (rule 5) and never goes into git or workflow artifacts. `.gitignore` covers `*.tfstate*`, `.terraform/` and any `*.tfvars` that holds secrets.

#### If your project uses database migrations

36. The migration step (e.g. `alembic upgrade head`) runs on the CI runner, signed in to the database with the pipeline's OIDC identity through Entra auth (no password). It adds a temporary database firewall rule for the runner's public IP and removes it in a cleanup step that always runs, even on failure. A failed migration stops the deploy, so later stacks run only after a successful migration.

## Commonly deferred (revisit triggers)

| Item | Revisit when |
| --- | --- |
| Additional environments | A second environment is needed: add `infra/<env>/<stack>` roots, same layout. |
| Terragrunt or other orchestration | More than ~3 environments or stacks make root duplication painful. |
| pre-commit hooks, terraform-docs automation, tflint/checkov | The CI/CD pipeline (rules 31-35) is working. |
| Key Vault, private networking | Real data or compliance comes into scope (azure.md). |
| State locking/lease tuning, state storage redundancy beyond defaults | Real data or more than one operator. |
